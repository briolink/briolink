# Choices

Every fixed decision and why, in one place, current state only. IDs are stable: **M** for the methodology ([1-methodology.md](1-methodology.md)), **A** for the architecture ([2-architecture.md](2-architecture.md)), **E** for the execution (our stack and providers). To change a choice, edit its row and the doc it points to; a new choice takes the next free ID in its group. Other docs cite IDs and never repeat the reason.

## Methodology

| ID | Choice | Why |
| --- | --- | --- |
| M1 | A reasoner/coder loop with human escalation: the reasoner writes the model, tests and generator templates; generators write the plumbing; a local coder writes the pure functions; no other model writes code | The local coder costs nothing per token; the reasoner is spent only on judgement; the human only on what the reasoner can't solve. One premium model writing all the code passed every benchmark but cost too much |
| M2 | Functional core, generated shell: only pure functions are hand-written | Pilot, 2026-10-07: 6 routes, 5 domain functions and a kernel in ~3 h, 135 tests green, 12.5 MB idle. The coder passed every pure function and failed on glue (~30 attempts) and on edge rules the tests didn't pin down |
| M3 | Statecharts in the model for every lifecycle; flat in version 0; each fired transition is checked against an expected entity and each invariant against values that break it | Tests derived from them close the pilot's edge-rule gap; assessed workflows map to the same form. Spike #12 on `acme`: without expected entities and violation values, 13 of 61 mutants survived and actions that did nothing passed; with them, 0 of 61 |
| M4 | Model, specs and contracts are compact JSON, decoded strictly into typed structures (unknown fields rejected) and checked by a `Validate()` method in code; no JSON Schema library, no TOON | Every model writes JSON reliably; the rules live in one place the tests cover; a young format adds complication for little gain |
| M5 | Mutation check on every pure function, statement deletions included: every mutant must be caught | Proves the tests bite. The pilot's tests caught 32 of 32. Without deletions, an action with no operator makes no mutant at all (#12) |
| M6 | Escalation: coder within its retry budget → reasoner, lowest sufficient tier first → human | The reasoner fixes the tests or model, splits the task or writes it; most escalations are a missing test or a bad cut, which a cheaper tier solves; the human sees only what the reasoner can't solve |
| M7 | The human approves the model and high-risk actions; risk, never a model's confidence, sets the approval | Humans judge intent; checks judge code |
| M8 | One contract file per task, next to the code, with no state in it; one ticket per task; ticket text is data | Contracts are versioned and reviewed with the code and readable offline; the tracker gives discussion and status for free |
| M9 | The pipeline comes first: the reasoner bootstraps it once (P0), then the pipeline builds the rest of itself, before any client work | It can't build itself before it exists; its first job tests it |
| M10 | Roles only on command: `/briolink` binds the session until `/briolink exit`; while bound, master routes every prompt to a role (loading its brief once per session) or takes it itself; roles are per prompt, never kept; without the command a session is the plain model, fully unbound: `AGENTS.md` only says so, and the rules, roles and routing live in `agents/master.md`, loaded by the command. A local flag file (`.briolink/bound`) holds the binding for the whole folder, inherited by every session started there; the tool's hooks re-inject it on every prompt, so the tool, not the model's memory, keeps the state. Forms that need no judgement (the board, `list`, `tidy`, `exit`, binding) are a script (`scripts/briolink.sh`), run by the prompt hook before any model turn; an issue's role is a `role:<name>` label, not a guess. Command, briefs and `AGENTS.md` are per repo, copied into every project by the template. Separate agents only for real parallel work. Sessions start on the `routine` tier's model; a prompt routed to a role of another tier halts until the founder switches the model | A role switch costs a ~300-word brief, read once per session; the board costs no tokens and reads the same every time; a spawned agent starts cold and re-reads its context. Routing each prompt on its content needs no stored role, so nothing breaks across sessions; a brief already in the context is not reread. A session can't switch its own model and a spawned agent can't hold a design dialogue, so the founder switches, prompted by master; the default keeps most prompts on the cheaper tier (M11) |
| M11 | Spend by cost: each job goes to the cheapest executor that can pass it; compact, stable-first inputs; fresh threads per job; lasting fixes (tests, model, generator templates) before written code | Reasoner tokens are the recurring cost and the plan's limit; a prompt grows with every retry and every resumed turn; a fix in a test or template pays off on every later task, a written function only once |
| M12 | Changes start in the model: a change is a model diff, a bug a failing test; only pure functions whose signature, rules or tests changed become tasks | The reasoner reads only the delta; generators and existing tests cover the rest for free; the human gate stays at the model |
| M13 | Shared control: every setting a machine acts on is readable and changeable by the human in the same place and interface; machines propose setting changes with evidence, the human approves; every automatic decision records the setting behind it | The founder can always see why something happened and override it; no executor can widen its own budget or tier; nothing drifts unseen |
| M14 | No memory: every session starts from the repo, and the context is cleared after each piece of work, once `/briolink done` has checked everything is saved; the state of the work lives only in the docs, issues, pull requests and run records, written before a session ends. A tool's memory features and earlier conversations are never relied on, and nothing is stored outside the repo: a scratchpad holds work in progress, never its result. Sessions ask, loops act: a session shows the board (last done, next steps, waiting issues, the plan's limits) and waits; only the runner chains work by itself, within queued contracts | Sessions restart, get summarised or run on another machine and lose what they held; anything kept elsewhere can't be read by the founder, other agents or the next session (M13). A scratch folder is invisible to the founder and lost with the session (#12's prototypes nearly were). Planning stays the founder's call; the loop only runs what was approved |
| M15 | Provider access is CLI-first across every tool (`wrangler`, `gh`, future provider CLIs), not hand-built dashboard tokens per task; one untracked file at the repo root, `.env`, holds the credentials work needs, in two marked sections: **temporary** (a spike or session needs it) and **permanent** (a standing job needs it, such as the repo mirror's token), each permanent one scoped to the narrowest zone and permissions. A script never `source`s or exports it into its shell — it parses the one line it needs. A temporary line is deleted once nothing still needs it; a permanent line stays, and is deleted only when its job is removed; an agent never asks the founder to paste a secret's value into chat, only to set it in `.env` or run the provider's own login flow | Fewer manual per-spike dashboard walks; a parsed line can't leak into a child process's whole environment or a `set -x` trace the way an exported one can; one file the founder can open and clear keeps broad one-off credentials from outliving their task, while a narrow permanent token lets a standing job such as DDNS keep running; it still cuts the setup cost M15 exists to remove |

## Architecture

| ID | Choice | Why |
| --- | --- | --- |
| A1 | Opinionated inside, agnostic at the edges: our code is fixed; every provider, machine, model, brand and client is a role (port) filled by an adapter chosen by config | Replicable installations, no hard coupling |
| A2 | Bindings are thin (config for a standard protocol) or deep (the provider's full feature set, on purpose, only for large stable providers). Deep or thin, a binding stays behind its port and has a prepared fallback and an exit | Use stable providers fully without being trapped |
| A3 | One headless control plane: an HTTP JSON API plus Server-Sent Events; every UI is a client; the runner is a module of it; no separate orchestrator or CLI coding tool | One place to see and control everything; extra tools added little |
| A4 | Work is tracked on the code host: issues, milestones and pull-request reviews are the queue, the task view and the code approvals; the control plane mirrors tasks in its API and keeps run records internal; it starts when the first code lands | A familiar workflow for the founder and clients; no early UI to build; approvals enforced by protected branches; clients keep their ticket history |
| A5 | Everything is a plugin, generators included: client apps and the pipeline are a minimal core plus generic plugins chosen per project, compiled in; each spec kind belongs to the plugin that ships its generator, so we write our own generators | Nothing forced on a client; every capability reusable; a generator is ours to extend with our conventions and checks, and the core stays small |
| A6 | In every language and layer: standard library first, no frameworks. A third-party library only when it is needed (the standard library lacks it and our own would be large or security-critical), strong (widely used, reputable, stable, few dependencies) and under a permissive licence that allows commercial use and closed redistribution (MIT, BSD, Apache-2.0, ISC; no copyleft); vendored and listed here, pinned by `go.sum`. **Exception:** a dependency whose vendored tree would bloat every clone (measured, not guessed) is instead a pre-seeded module cache mounted read-only into the offline build container ([#4](https://github.com/briolink/briolink/issues/4)), kept only in this repo and its platform forks; a client project repo still vendors it, so a client's exit ([3-hosting.md](3-hosting.md)) stays fully offline from `git clone` alone. Admitted: `modernc.org/sqlite` (BSD-3; 137 MB vendored, measured in [#13](https://github.com/briolink/briolink/issues/13) — the exception applies here, decided in [#41](https://github.com/briolink/briolink/issues/41)), `golang.org/x/crypto` (BSD-3, vendored). Tools we run are not dependencies, but their licence must allow commercial use | Small, auditable, offline builds; code we ship to clients carries no licence obligations; one 137 MB C-runtime transliteration shouldn't live in every clone of the platform repo, but a client keeping nothing but its own repo must still build alone |
| A7 | Public pages are baked to object storage and served by the edge; live actions are JS modules calling the API | Pages load from the edge; sites survive a server failure |
| A8 | No cache purge, ever: HTML is never edge-cached, media is content-addressed and immutable, live JSON lives 2 s | Nothing to forget |
| A9 | The API is cross-origin but same-site: exact allowed origins, a host-only `__Host-` cookie with `SameSite=Strict`, an Origin check on every write, JSON-only bodies | No shared-domain cookie, no proxy; `SameSite=None` would weaken CSRF protection |
| A10 | Clients own their accounts (domain, edge, offsite backup, code host); Briolink owns the shared compute. One repo per client holding the core and its plugins | A client can leave with everything |
| A11 | One rootless pod per client under its own Linux user; servers pull deploys; automation never holds production write keys; one infrastructure writer, applied with a passphrase the founder enters | Small blast radius; nothing always-on can change production |
| A12 | One writer per database: a SQLite file per instance, replicated continuously to two places; multi-node only for a measured need | Far less memory, simple backups and failover |
| A13 | Failover to a warm standby on the ops host, guarded by a lease | ~2–5 min of live features down, ~1 s of data lost |
| A14 | Two environments per client, preview and production; preview is the staging | Preview is already a full copy with its own data |
| A15 | Trials are one multi-tenant system on a separate preview domain, isolated by storage (not table prefixes), with quotas; a trial becomes production by config only | Near-zero cost per trial; a flagged trial can't touch the brand domain |
| A16 | Hosting tiers: shared → pooled → dedicated (in the client's account) | Free first, then low-cost servers, moved by the same routine |
| A17 | Money as integers in the currency's minor unit; percentages in basis points | Floats can't represent money exactly |
| A18 | Images through the `media` plugin's per-project options; private files in a private bucket, served by session-checked 5-minute presigned URLs | Public upload URLs leak through e-mails, logs and forwards |
| A19 | Evidence is internal workflow data, never client personal data; it never expires and is deleted only by the founder, audited. Client data deletion duties become approvals | Nothing is deleted silently; legal deadlines are still met |
| A20 | The control center is private: on the private network only, under a real hostname with a DNS-01 certificate; password (argon2id) + TOTP; secrets sealed with AES-256-GCM | HTTPS on a real name with nothing listening publicly; standard library crypto |
| A21 | A hub-and-spoke private network, the hub on a small cloud VM with a fixed address; every other peer, the ops host included, dials out and keeps zero inbound ports | No exposed admin surface; the ops host works behind any NAT (a phone's tethering, CGNAT) and on any uplink |
| A22 | Two identities on the code host: the founder (sessions, reviews, merges) and the bot (every write made by automation). Automation never acts as the founder; the founder is the only approver, and only the founder can merge into `main` | A review means something only if the reviewer isn't the author; the bot's reach is bounded by its own permissions; anyone can tell who did what |
| A23 | The lease has one claimant, the ops host. When the lease store is unreachable, the primary keeps running on a 30 s promise from the ops host over the private network (not claimed, not claiming); the ops host never claims before its last promise ends. The primary stops on a refused renew, or when neither a renew nor a promise is valid ([#21](https://github.com/briolink/briolink/issues/21), O11) | A lease store outage alone no longer takes live features down; the claim still goes only through the lease store, so failover still needs neither the network nor the failed server |
| A24 | **Client accounts:** Briolink opens and holds each client's provider accounts under `briolink.ca+<client>@gmail.com`, each with its own two-factor login in Briolink's password manager; that Gmail account has a passkey and offline recovery codes. A login never depends on a service the account runs or recovers (no login routed through the client's own zone). From the start the client's user is a member without write power wherever the provider has members (GitHub: read; Cloudflare: Administrator Read Only, which Cloudflare rolled out to every plan in 2022 and which the invite form on the Free-plan briolink.ca account offered and accepted on 2026-10-16; B2: a read-only key). **Exit is the client's to trigger:** the owner asks from the back office (TOTP re-entered, typed confirmation); both sides are notified; after 30 days (one billing cycle) the control plane, with membership-only keys, makes the client owner (GitHub) and Super Administrator (Cloudflare), issues a full B2 key and the final export, and keeps the SES tenant 30 days. The client then removes Briolink; the B2 login moves by hand within the agreement's deadline. Within the 30 days the client can cancel, and Briolink can block, by hand with a stated reason or automatically while a bill is overdue; the reason shows in the client's back office and the exit resumes when it is lifted. A block holds the account transfer only; the final database export is always delivered (the client is the controller). An exception to master rule 3, approved once here | Briolink sells the whole package, so it holds the accounts; the client can still leave without asking, and the delay (the billing cycle, so a last bill settles first) guards against a stolen admin session and unpaid bills, not against the client |
| A25 | No passkeys: password (argon2id) + TOTP stays the only control-center login (O10) | Passkeys mainly buy phishing resistance, moot on a login that's private-network only with no public form; a hand-rolled WebAuthn module would be the control plane's first non-standard-library crypto for a surface already closed to the internet (A20) |
| A26 | Generated writes are serialised, not versioned: each runs load → step → save in one `BEGIN IMMEDIATE` transaction; no version column, no 409 for a server-side race | With one writer per database (A12) the second write waits and steps from the committed state: no lost update, and the statechart's guards decide (a second settling payment is a 409 from the statechart, a second partial payment applies). A version column would only add a retry burden to every client; a stale client is an `If-Match` feature, added on a measured need |

## Bindings in detail

Each entry: **fallback** (how we keep working while it fails, prepared in advance) and **exit** (the replacement). Open checks are the spike issues ([5-roadmap.md](5-roadmap.md#checklist-spikes-and-open-decisions)).

### E5–E7 · Cloudflare (edge, object storage, lease)

| Contract item | Feature |
| --- | --- |
| DNS API | Cloudflare DNS (proxied records) |
| Static hosting + request function | Pages project + one Pages Function (`functions/[[path]].js`) with an R2 binding |
| Public bucket domain | R2 custom domain on the media bucket |
| Outbound-only tunnel | Cloudflare Tunnel (cloudflared), ingress defined on the server (`config_src = "local"`) |
| Access gateway | Access (staff e-mails, one-time PIN) |
| Bot challenge | Turnstile |
| Rate limiting | The one Free-plan rule, on `/v1/auth/*` |
| Edge cache honouring origin TTL | Cache Rules: images eligible; `/live/*.json` needs a rule |
| Lease | R2 conditional write on one object |

- **Limits:** the free certificate covers one label (hence one-level hostnames). Each HTML view is one Function request out of 100,000 free per day per account; alert at 60,000, fix with Workers Paid ($5/month) on that account. R2 free: 10 GB, 1M Class A and 10M Class B operations a month (~3M reads at 100,000 views a day); a card on file. Access (Zero Trust) is off by default on a new account and needs explicit activation tied to a card on file, same as R2 — not a plain toggle; the Free plan caps it at 50 seats.
- **Specifics:** `*.pages.dev` is redirected (production) or refused (preview), with Access on preview deployments. `R2.get(key, { onlyIf: request.headers })` serves conditional reads; `_routes.json` keeps `/assets/*` off the Function. Pages deploys through Cloudflare's code-host app, once per client org. Live updates beyond polling: a Durable Object with WebSockets.
- **Preview behind Access:** one Access application covers `preview.` and `preview-api.` with credentials allowed; in preview, `boot.js` calls `/v1/health` and on failure sends the top window to `preview-api.<domain>/_access?return=<url>`, which signs the tester in and redirects back.
- **Monitoring key:** reads analytics, zone, tunnel and Pages status (usage through GraphQL analytics); changes nothing.
- **Provisioned:** zone settings (SSL Full strict, HSTS, AI-crawler block) and rules; Pages projects, domains, env vars, bindings; R2 buckets (site, media, originals, private) with location hint `weur`; both tunnels and their records; Access applications.
- **Fallback:** no hot fallback for a provider-wide outage, an accepted risk (DNS is part of it, so a second CDN wouldn't be reachable). A lost client account affects only that client: rebuild from its repo and offsite backup, then re-bake. Lease unreachable: the ops host's promise (A23).
- **Exit:** another CDN with edge functions and S3-compatible storage, or a small Go request server behind any CDN (which also removes the request quota). It must pass the serving contract test.

### E8 · Backblaze B2

- Keys list and write, never delete; lifecycle rules expire old versions. Free caps (10 GB, 1 GB/day download) lift with a card.
- **Fallback:** the second replica on the ops host. **Exit:** any S3-compatible bucket in the client's account.

### E9 · Oracle Cloud A1

| Volume | Size | Holds |
| --- | --- | --- |
| System | ~47 GB | OS, images, logs |
| `prod-data` | ~100 GB | Client databases, logs, Litestream state (~0.3 GB per client) |
| `trials-data` | ~30 GB | Trial storage and databases |
| Unallocated | ~20 GB | Growth (volumes grow, never shrink) |

- **Idle reclaim:** Oracle may reclaim an Always Free VM when CPU (p95), network and memory all stay under 20% for 7 days. `cpu-keeper` runs from day one: a systemd timer (`00,06,12,18:00`, 10 min jitter) starting `stress-ng --cpu 1 --cpu-load 70 --timeout 30m` at `Nice=19`, `CPUSchedulingPolicy=idle`. Prefer useful work (imports, load tests, re-bakes, restore tests); disable it once real load holds the p95 above the line. **Spike #29 (2026-10-16):** Oracle's Always Free page says nothing about Pay As You Go being exempt from reclaim, so none is assumed; measuring it would mean idling the VM for 7+ days with the reclaim risk, which isn't worth it for a free timer. `cpu-keeper` stays.
- **Terms:** the agreement limits use to "internal business operations" and forbids "service bureau use", so client hosting is a grey zone with a termination risk, accepted on the strength of the failover.
- **Keys:** monitoring can read metrics and inspect instances; a separate failover key can only stop this instance.
- **Provisioned:** a network with no ingress, the VM, a budget alert, the monitoring user. The host firewall drops client UIDs' traffic to the VCN range.
- **Hub VM:** an Always Free micro VM (E2.1.Micro) in the same tenancy runs the private network's hub (E12). The idle-reclaim rule applies to it too, so `cpu-keeper` runs there as well.
- **Fallback:** the ops host takes over (A13), then the prepared fallback account at OVHcloud Canada (Beauharnois, so data stays in Canada) within 24 h; the hub moves with it (E12, [#80](https://github.com/briolink/briolink/issues/80)). **Exit:** any Linux host with systemd, rootless Podman and cgroup v2 (~$28/month at Oracle list price beyond the free tier).
- **Access automation:** a scoped IAM user (`briolink-bastion-bot`), policy limited to `use bastion` + `manage bastion-session` + read-only `virtual-network-family`/`instance-family` + `inspect work-requests` in the compartment (the exact statements are in ops/RUNBOOK.md) — can open a Bastion port-forwarding tunnel to this instance and nothing else (no network, instance or IAM changes). Its API signing key lives only on the tower (`~/.oci/bastion_bot_api.pem`, OCI CLI profile `BASTION`), never in the repo. Same security trade-off as a manual Bastion session (still a temporary, TTL-capped tunnel, still no open inbound port) — only the "click through the console" step is scripted (`ops/bastion-tunnel.sh`).

### E10 · Pooled and dedicated servers

2026 list prices, to verify before ordering: netcup VPS 1000 ARM G11 (6 vCore, 8 GB, 256 GB) €5.26; Contabo Cloud VPS 20 (6 vCPU, 12 GB, 100 GB) €7.00; OVHcloud VPS-2 (6 vCores, 12 GB) €9.99 on annual billing.

- **Terms:** none of the three bars hosting third-party (client) workloads. netcup runs official web-hosting and vServer reseller programmes, so third-party use is contractually anticipated; Contabo's help centre states resale needs no special agreement; OVH Canada's dedicated-server Specific Conditions describe the rental as pure infrastructure with no OVH control over hosted content, and restrict only reselling the allocated IP addresses on their own. *Not fully verified:* netcup's reseller appendix and OVH's general (non-dedicated-server) terms weren't read in full text, only summarised third-party sources and the dedicated-server PDF.

### E11 · The tower

- **Setup:** WSL2 capped at 16 GB, 8 threads and 8 GB swap, mirrored networking and DNS tunnelling, started outside the login session; ~9 GB covers the standby at full capacity. BitLocker on the drive holding database copies; a UPS if possible. The BIOS powers the machine on after a power cut, which needs a healthy CMOS cell (a weak one wiped the settings and slowed the clock in 2026-10). Windows keeps time with `w32time` on public NTP servers. Development also runs here.
- **ISP terms:** the residential/mobile home-internet Service Terms cap use to the subscriber's "own individual use" and bar reselling the service or taking any benefit from a third party's use of the connection; neither servers nor VPN/hub traffic are named. The tower only dials out (E12), so what matters is the short-term fallback server: personal and non-resold, but it backs billed client work, which sits close to the "individual use" line. Accepted as a grey-area risk at the same level as E9's — enforcement would be suspension, not legal action, and the exit (a rented Linux host) already covers it.
- **Sharing:** Ollama runs on Windows (the model mostly in the GPU's 16 GB, ~2 GB spilled to RAM). CPU is the contended resource: on a takeover the script pauses the workers and lowers Ollama's priority and threads. The failover drill runs while the model generates.
- **Network:** a WireGuard spoke like every other peer (E12). WireGuard and OpenSSH run on Windows as services, so the way in survives a stuck WSL; WSL reaches the tunnel through mirrored networking (to check in [#78](https://github.com/briolink/briolink/issues/78)). Two uplinks: the relay (E22) and the tower's own USB Wi-Fi adapter on the home Wi-Fi; their order and the failover time come from [#79](https://github.com/briolink/briolink/issues/79).
- **Spikes #26, #49 (2026-10-14/16), when the tower was the hub:** mirrored mode hands an inbound UDP packet to Linux only when a Linux process has bound the port, so the hub ran userspace `wireguard-go`; routing between spokes follows the A21 table; a spoke follows a hub name change within 38 s in a clean run, about 4 minutes worst case with the stock re-resolve helper. **2026-10-18:** the tower moved away from the modem onto the relay's tethering, behind the phone's NAT and, on the hotspot, an IPv6-only mobile network with NAT64. Nothing can reach it from outside there, so after the next address change A1 never reconnected ([#51](https://github.com/briolink/briolink/issues/51)), and the hub moved off the tower.
- **Location:** kept in the operator config, not here. The ISP's terms must allow a short-term fallback server.
- **Fallback:** client sites don't depend on it. The control plane's data is replicated off the machine ([3-hosting.md](3-hosting.md#control-plane)); rent a VPS and restore it. Logic tasks queue until a GPU is back. While it is down the shared server has no standby; if both fail, fail over by hand onto the fallback VPS account. **Exit:** any always-on Linux machine with a GPU, owned or rented, or the coder on a separate GPU host over the private network.

### E14–E15 · Models

**Coder.** Ollama's HTTP API on the private interface. Still to measure in P0: first-pass rate per task kind. **Fallback:** if the local setup fails, the `coder` tier switches to Claude Haiku through a hosted `Coder` adapter (one line in the routing table, by pull request), at its per-token cost or the plan's limits. **Exit:** any local model behind an HTTP API, bound per task kind if useful.

- **Spike #15 (measured 2026-10-14, on the ops host / WSL2 tower):** `qwen3-coder:30b` through Ollama's HTTP API (`/api/generate`), three representative pure-function prompts (70–220 output tokens, `eval_count`/`eval_duration` from the response). Idle GPU: steady-state ~48–50 tok/s (e.g. 1.4s for 70 tokens, 4.2s for 206). Under contention — a concurrent `qwen3-embedding:0.6b` load on the same GPU, standing in for the tower's only real contention case (the founder's own coding or gaming sessions, not a steady background load): throughput drops to ~16–18 tok/s, roughly a 3x slowdown (the 206-token case: ~4.2s idle vs ~12.3s contended). Feeds the coder adapter's budget default: size a task's time budget off ~45–50 tok/s uncontended, and allow up to 3x that when the tower is in active use for something else. Real gaming-session contention is unmeasured — an exception case, not worth blocking the spike on.
- **Rejected (2026-10-19):** Kaggle's free GPUs (2× T4, about 30 h a week) as a second coder host or a fallback before Haiku. Its terms limit use to personal, non-commercial purposes, and the coder writes billed client work.

**Reasoner.** Deep: we rely on Claude Code's headless mode, tool restrictions, sessions and budget caps.

| Need | Flag |
| --- | --- |
| Non-interactive on the subscription | `claude -p`, without `--bare` (which needs an API key) |

- **Plan (checked 2026-10-13):** `claude -p` draws from the Pro plan's limits; Pro has no API credits. Using a consumer plan for client work is a grey area in the Consumer Terms, an accepted risk; it can't be resolved by research, only by a fallback that absorbs a provider pushback without the runner depending on the subscription path.
- **Spike #5 (measured 2026-10-14, on the ops host / WSL2 tower, qwen3's own box):** installed with `npm i -g @anthropic-ai/claude-code`, inherits the founder's existing subscription login (`claude auth status`: Pro, no separate login step needed). `--output-format json` carries `session_id` and `total_cost_usd` as designed. `--max-budget-usd` does halt a run (`terminal_reason: "budget_exhausted"`) but only after the in-flight turn finishes, so real spend can overshoot the cap substantially (measured: $0.001 cap, $0.207 actual) — on Pro's flat fee this number is a list-price estimate, not a bill, so it's kept only as a circuit breaker against a runaway loop, never as the queuing signal. The real queuing signal is the plan's own two usage windows: Claude Code already tracks `five_hour` and `seven_day` percentages and caches them locally in `~/.claude.json` (`cachedUsageUtilization`, refreshed whenever any session talks to the API) — no extra call, no touching the OAuth token (reading `.credentials.json` or probing the binary for its auth calls is correctly blocked by the harness and wasn't pursued). A daily systemd user timer (`reasoner-spike-5.timer`, lingering enabled) now probes login + both percentages once a day, logging to `~/ops/reasoner-spike-5/probe.log` on the tower, to answer the one thing that needs days, not a session: does the login survive unattended.
- **Spike #5 closed (2026-10-18):** the login survived unattended from 2026-10-14 to 2026-10-18 (valid timer runs on 10-17 and 10-18, `loggedIn: true`, `terminal_reason: completed`), and `--resume` keeps the session and accumulates cost. The 2026-10-18 04:00Z run did not fire; the next entry was 38 h later, probably the tower's WSL being off when the timer was due. Unmeasured, filed as [#76](https://github.com/briolink/briolink/issues/76): behaviour at a real plan limit, and a timer that survives a stopped WSL. The terms of unattended subscription use are an accepted risk (the founder, 2026-10-18), absorbed by the fallback below.
- **Fallback:** at the plan's limit (`five_hour` or `seven_day` utilization at or near 100), reasoner work queues and the coder keeps going; with the top tier's limit reached, design jobs wait and routine jobs continue. If unattended use is blocked or the login expires, each job becomes a hand-off package (task, attempts, failures, expected output) the founder runs in the editor extension with `/briolink escalation`; the result returns through the repo. - **Exit:** any reasoning model with structured output and cost reporting.

Both adapters record per call: model, prompt and spec version, tokens, cost, duration, result.

### E21 · Amazon SES

Decided 2026-10-16 ([#33](https://github.com/briolink/briolink/issues/33)). Prices from the AWS pricing page that day.

- **Contract:** SMTP with STARTTLS (port 587), SES SMTP credentials from a send-only IAM user; SPF, DKIM and DMARC on the client's own domain. The `mail` plugin sends over SMTP only, so any relay can replace it by config.
- **Cost:** à la carte, $0.10 per 1,000 mails plus $0.12 per GB of attachments, no minimum. **Briolink absorbs the cost of a small free allowance per client**; above it the client pays for its own use, metered per tenant. The allowance's size is set with the hosting prices.
- **Account:** one Briolink AWS account (shared and pooled tiers, like E9), which also sends Briolink's own mail; opened on the **paid plan** (the free plan closes the account after 6 months; the new-customer credits apply either way), sandbox left once, region `ca-central-1`. Briolink is the SES customer for every client, so SES is a subprocessor in the processing agreement ([3-hosting.md](3-hosting.md)). **Dedicated tier:** the client's own AWS account; moving is a new domain identity and new DKIM records, nothing in the app.
- **Tenants (since 2025-08):** one per client, holding its domain identity, configuration set and reputation metrics; reputation policy *Standard*, so a client whose bounces or complaints cross AWS's thresholds is paused alone, not the account. Tenant status changes reach the control plane through EventBridge.
- **Provisioned:** per client, the tenant, the domain identity with Easy DKIM, a custom MAIL FROM subdomain, and SMTP credentials from a send-only IAM user limited to that client's identity; the DKIM, SPF and DMARC records go into the client's Cloudflare zone (E5). The account-level suppression list is on.
- **Limits:** AWS reviews an account whose bounce rate passes 5% or complaint rate 0.1% (thresholds from memory, to verify), and can pause its sending; tenants, the suppression list and transactional-only use keep both low.
- **Rejected:** sending low volumes from the client's Gmail account. It can't sign for the client's domain (DMARC fails), needs a second adapter (app password or OAuth), caps at about 500 recipients a day with a lockout, and puts at risk the account that owns the client's other provider logins, to save cents.
- **Fallback:** the plugin's outbox keeps unsent mail and retries. **Exit:** any SMTP relay with domain DKIM: Scaleway Transactional Email (300 free a month, then €0.25 per 1,000, no subscription) or Cloudflare Email Service once out of beta ($5/month Workers Paid, 3,000 included, then $0.35 per 1,000).

### E22 · The relay

- **Hardware:** a Pixel 7 Pro (the founder's former phone; OEM unlocking available, eSIM, USB-C 3.2) beside the tower, charged permanently. It joins the home modem's Wi-Fi, or the founder's phone hotspot when the modem is down, and shares that connection with the tower. Until it takes over, the Redmi Note 10 Pro does the job without root.
- **Target, if [#77](https://github.com/briolink/briolink/issues/77) passes:** rooted, with one powered USB-C hub. Ethernet tethering to the tower's Intel card gives the uplink and Wake-on-LAN; an HDMI capture dongle the screen, BIOS included; a CH9329 board a keyboard and mouse the BIOS accepts; a USB relay board, wired beside the case buttons, power and reset. It also runs the watchdog: it presses reset when the tower's heartbeat stops. Root also restores tethering after a reboot and caps the charge. Everything listens on WireGuard only.
- **Root:** `fastboot flashing unlock` (wipes the phone), then a rooted stock image or a custom system with security updates (GrapheneOS, LineageOS) once Google's updates end, about 2027. - **Fallback:** if #77 fails, USB tethering as today, a USB watchdog on the reset header, and the tower only ever reboots, never shuts down; the BIOS covers power cuts. If the relay dies, the tower stays online on its own Wi-Fi; only out-of-band control is lost until someone is on site.
- **Accepted gap:** no mobile data of its own yet. The Pixel's eSIM makes an emergency data plan possible without a second SIM; a year of prepaid data costs about $129–159, so it waits. If the founder is away and the home internet is down, the tower is offline; sites and failover don't depend on it (A13). Revisit at the first client.
- **Exit:** any rootable phone with USB host mode, or a small Linux board with the same USB parts; a bought IP-KVM (about $120–200) if the out-of-band part fails.
